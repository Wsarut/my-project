Security Fundamentals

พื้นฐานการอ่านเหตุการณ์ใน Lab

หน้านี้รวบรวมแนวคิดหลักก่อนเข้าสู่ห้องจำลอง ผู้เรียนไม่จำเป็นต้องท่องจำคำศัพท์ทั้งหมด แต่ควรเข้าใจว่าข้อมูลใดต้องปกป้อง ระบบควรตรวจอะไร และผู้ดูแลควรตอบสนองอย่างไรเมื่อเห็นอาการผิดปกติ

ข้อมูลต้องถูกมองเห็นเท่าที่จำเป็นบัญชี ลูกค้า session และคำสั่งซื้อควรถูกจำกัดตามสิทธิ์
ข้อมูลต้องไม่ถูกเปลี่ยนโดยไม่มีหลักฐานเนื้อหา ราคา inventory และสถานะธุรกรรมต้องตรวจย้อนกลับได้
ระบบต้องฟื้นตัวได้อย่างมีขั้นตอนการกู้คืนควรมาจากการตรวจขอบเขต ยืนยันหลักฐาน และคืนค่าที่เชื่อถือได้

Project Overview

เรียนรู้จากสิ่งที่เกิดขึ้นกับระบบ ไม่ใช่เพียงจำชื่อภัยคุกคาม

โครงการนี้จัดทำขึ้นเพื่อช่วยให้ผู้เรียนเข้าใจความสัมพันธ์ระหว่างพฤติกรรมผิดปกติ ผลกระทบที่ผู้ใช้งานมองเห็น และข้อมูลหลังบ้านที่ผู้ดูแลระบบใช้ตัดสินใจ เนื้อหาครอบคลุมเว็บไซต์ข่าวสาร ร้านค้าออนไลน์ และระบบจำหน่ายตั๋ว ซึ่งมีข้อมูลและความเสี่ยงต่างกันอย่างชัดเจน

ขอบเขตเพื่อการศึกษา: เว็บไซต์ บัญชีผู้ใช้ ข้อมูลลูกค้า คำสั่งซื้อ การชำระเงิน และบัตรเข้างานทั้งหมดในโครงการเป็นข้อมูลจำลอง ไม่มีการเชื่อมต่อธุรกรรมจริง และไม่ควรนำคำสั่งหรือแนวทางไปใช้กับระบบที่ไม่ได้รับอนุญาต

Simulation Format

ในห้องจำลองจะเกิดอะไรขึ้นบ้าง

ห้องจำลองถูกออกแบบให้ผู้เรียนเห็นทั้งด้านหน้าเว็บไซต์และสิ่งที่เกิดขึ้นในระบบเบื้องหลัง โดยมีบทบาทการโจมตีและการป้องกันแยกกันชัดเจน เพื่อให้เข้าใจว่าคำสั่งหนึ่งคำสั่งส่งผลต่อข้อมูล หน้าเว็บ และขั้นตอนกู้คืนอย่างไร

Attack View จำลองผลกระทบจากการโจมตี

ผู้เรียนจะใช้คำสั่งเพื่อสร้างอาการผิดปกติในเว็บไซต์ เช่น เนื้อหาถูกเปลี่ยน ข้อมูลลูกค้าถูกเข้าถึง ราคาไม่ตรง หรือจำนวนตั๋วผิดปกติ แล้วสังเกตว่าผลกระทบปรากฏตรงไหน

Defense View จำลองขั้นตอนการป้องกัน

ฝ่ายป้องกันไม่ได้แก้ทุกอย่างด้วยปุ่มเดียว แต่ต้อง scan, ตรวจขอบเขต, เปิดการตรวจสอบ, ยืนยันข้อมูล และกู้คืนตามลำดับ เพื่อให้เห็นเหตุผลของการตอบสนองแต่ละขั้น

Evidence View อ่านหลักฐานจากหลายจุด

หน้าเว็บใน iframe แสดงอาการที่ผู้ใช้ทั่วไปอาจมองเห็น ส่วน Mission Console, Situation Panel, Operation Log และ DATA LINK CONSOLE ช่วยบอกข้อมูลระบบที่ต้องใช้วิเคราะห์ประกอบกัน

Core Model

มองความปลอดภัยผ่านคุณสมบัติของข้อมูล

Lab ทั้งหมดใช้กรอบคิดเดียวกัน คือดูว่าข้อมูลถูกเปิดเผย ถูกแก้ไข หรือถูกทำให้ใช้งานไม่ได้หรือไม่ จากนั้นจึงเลือกคำสั่งและขั้นตอนป้องกันที่เหมาะกับอาการของแต่ละเว็บไซต์

Confidentiality

ข้อมูลสำคัญควรเข้าถึงได้เฉพาะผู้ใช้ ระบบ หรือกระบวนการที่มีสิทธิ์ เช่น ข้อมูลลูกค้า session token และรายละเอียดบัญชี

Integrity

ข้อมูลต้องตรงกับแหล่งที่เชื่อถือได้ เช่น เนื้อหาข่าว ราคา จำนวนตั๋ว และสถานะคำสั่งซื้อ หากเปลี่ยนต้องมีที่มาและตรวจสอบได้

Availability

ระบบควรพร้อมให้ผู้ใช้ทั่วไปใช้งาน แม้มีคำขอผิดปกติ คิวแออัด หรือการกระทำที่พยายามทำให้บริการเสียสมดุล

Web Control Concepts

สิ่งที่เว็บควรตรวจ ไม่ใช่แค่สิ่งที่ผู้ใช้มองเห็น

หลายเหตุการณ์ใน Lab ไม่ได้ทำให้หน้าเว็บพังทันที แต่อยู่ในข้อมูลหลังบ้าน เช่น ราคาไม่ตรงกับฝั่งระบบ จำนวนตั๋วไม่สัมพันธ์กับ inventory หรือมีการอ่านข้อมูลลูกค้าจากช่องทางที่ไม่ควรเกิดขึ้น

Authentication

ยืนยันว่าใครกำลังใช้งานระบบ และ session นั้นยังน่าเชื่อถือหรือไม่

Authorization

ตรวจว่าผู้ใช้หรือกระบวนการนั้นมีสิทธิ์ทำสิ่งที่กำลังร้องขอจริงหรือไม่

Server-side Validation

ตรวจข้อมูลสำคัญที่ฝั่งระบบ เช่น ราคา จำนวนสินค้า จำนวนตั๋ว และลำดับคำสั่งซื้อ

Integrity Baseline

ใช้ข้อมูลตั้งต้นหรือแหล่งอ้างอิงเพื่อเทียบว่าข้อมูลปัจจุบันถูกแก้ไขผิดปกติหรือไม่

Rate & Bot Control

มองหาคำขอถี่ผิดปกติ พฤติกรรมซ้ำ และการซื้อจำนวนมากในช่วงเวลาสั้น

Audit & Recovery

เก็บร่องรอยเหตุการณ์ ตรวจขอบเขตผลกระทบ และกู้คืนจากข้อมูลที่เชื่อถือได้

Security Principles

มองความปลอดภัยผ่านคุณสมบัติของข้อมูล

สถานการณ์ในโครงการไม่ได้วัดเพียงว่าเว็บไซต์เปิดได้หรือไม่ แต่ชวนตรวจว่าข้อมูลถูกเปิดเผย ถูกเปลี่ยน หรือไม่พร้อมให้ผู้ใช้ที่ควรเข้าถึงหรือไม่

Confidentiality

ข้อมูลลูกค้า บัญชี และ session ต้องเข้าถึงได้เฉพาะบุคคลและระบบที่ได้รับอนุญาต

Integrity

เนื้อหา ราคา คำสั่งซื้อ และจำนวนตั๋วต้องตรวจสอบย้อนกลับและเทียบกับแหล่งข้อมูลที่เชื่อถือได้

Availability

ระบบต้องพร้อมให้ผู้ใช้ทั่วไปเข้าถึงได้ แม้เผชิญคำขอผิดปกติหรือเหตุการณ์ที่กระทบทรัพยากร

Response Flow

ลำดับคิดเมื่อเจออาการผิดปกติ

การป้องกันใน Lab ถูกออกแบบให้ไม่ใช่การกดรีเซ็ตทันที ผู้เรียนควรอ่านอาการ ตรวจขอบเขต จำกัดผลกระทบ ยืนยันข้อมูล และกู้คืนตามลำดับที่มีเหตุผล

01Observe

สังเกตสิ่งที่เปลี่ยนบนหน้าเว็บและ Operation Log

02Scope

แยกว่าปัญหาอยู่ที่ content, customer, checkout, inventory หรือ identity

03Contain

จำกัดช่องทางที่กำลังทำให้ข้อมูลเปลี่ยนหรือรั่วไหล

04Verify

เทียบกับ baseline, server record หรือ ledger ที่น่าเชื่อถือ

05Restore

คืนค่าที่ถูกต้องหลังรู้ขอบเขตและยืนยันหลักฐานแล้ว

06Review

อ่านรายงานผลเพื่อเข้าใจผลกระทบและการป้องกันที่ใช้

Connect To Labs

หลักการเดียวกัน แต่ผลกระทบคนละแบบ

แต่ละห้องจำลองเลือกเน้นข้อมูลสำคัญต่างกัน เพื่อให้ผู้เรียนเห็นว่าความปลอดภัยเว็บไม่ได้มีหน้าตาเดียว ข่าวสารเน้นความถูกต้องของเนื้อหา ร้านค้าเน้นข้อมูลลูกค้าและธุรกรรม ส่วนเว็บตั๋วเน้นจำนวนตั๋ว คิว และตัวตนผู้ซื้อ

News Lab

ฝึกสังเกต integrity ของเนื้อหา หน้าแรก และ publish baseline เมื่อข้อความถูกแก้หรือถูกแทรกองค์ประกอบผิดปกติ

Shop Lab

ฝึกมองข้อมูลหลังบ้าน เช่น customer profile, server price, checkout sequence และการกู้คืนคำสั่งซื้อที่ผิดปกติ

Ticket Lab

ฝึกวิเคราะห์ inventory, queue, identity และพฤติกรรมซื้อจำนวนมากที่ทำให้ผู้ใช้ทั่วไปเสียโอกาส
